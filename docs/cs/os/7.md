## Locks

我们通过引入**锁**（lock）来保证临界区代码的原子性，假设临界区的代码如下：

```python
balance = balance + 1;
```

在使用锁保护临界区后，代码类似于

```c
lock_t mutex;

lock(&mutex);
balance = balance + 1;
unlock(&mutex);
```

锁是一个保存了自身状态的变量，其内部也可包含其他对用户透明的隐藏信息。锁有以下两种状态

1. **可用的**（available / unlocked / free）：无线程持有锁。
2. **被占用的**（acquired / locked / held）：某线程正持有锁并执行临界区代码。

锁主要有以下两种操作：

- **加锁（`lock`）**：调用 `lock` 的线程会尝试获取锁。若锁可用，线程将获取锁并进入临界区；若锁已被其他线程持有，当前线程的 `lock` 调用将阻塞（不会返回），直到锁被释放。
- **解锁（`unlock`）**：锁的持有者调用 `unlock` 会释放锁。此时，若无其他线程等待，锁将恢复为“可用”状态；若有线程正在等待该锁，则其中一个等待线程会成功获取锁并进入临界区。

线程默认由操作系统随意调度，而**锁**通过限制代码段的并发，让程序员拥有了部分控制权，从而将混乱无序的调度变得更加可控

!!! info "Coarse-Grained or Fine-Grained Locking"
    相较于所有临界区共用一把锁（**粗粒度**, coarse-grained），用不同的锁保护不同的数据或临界区（**细粒度**, fine-grained），能让更多线程同时进入不同的临界区，从而提升系统的**并发度**

### Evaluating Locks

可以通过下面三个维度评判锁的实现是否良好：

- **互斥**(mutual exclusion)：锁**最基本的作用**，即能否有效阻止多个线程同时进入临界区
- **公平性**(fairness)：竞争锁的线程能否公平地获得锁，避免出现**饥饿**(starvation)
- **性能**(performance)：需要综合考虑无竞争（单线程）、单核 CPU 下的多线程竞争、以及多核 CPU 下的多线程竞争三种情况下，使用锁增加的时间成本

接下来，我们将使用几种不同的软硬件机制来构建锁，并根据上面的维度来评估它们的表现

### Controlling Interrupts

在早期的**单处理器**系统上，实现互斥的方法是在进入临界区之前**关闭中断**。其伪代码如下：

```c
void lock() {
	DisableInterrupts();
}

void unlock() {
	EnableInterrupts();
}
```

在一个单处理器系统上，在进入临界区之前关闭中断意味着在临界区内不会发生上下文切换，从而保证了临界区代码的原子性。在执行完临界区代码后重新打开中断，系统将像平时一样继续运行

这种方法的优点是实现起来非常简单，但是存在着以下三个缺点：

- 关闭和开启中断需要使用**特权指令**，恶意程序可能会滥用这一机制，导致操作系统失去控制权
- 在多核处理器中，该方法无效。当运行在多个处理器上的线程进入同一个临界区时，系统只能关闭当前处理器上的中断，运行在其他处理器上的线程仍然能够进入临界区
- 长时间关闭中断会导致 CPU 错过重要的硬件信号，从而引发严重的系统问题

基于以上原因，通过关闭中断实现互斥的方法，通常只在**操作系统内部**使用

### Loads/Stores

由于关闭中断实现锁存在诸多缺点，我们需要使用其他的软硬件机制来构建锁

首先尝试使用一个简单的变量 `flag` 来表示是否有线程拥有锁，并使用加载与存储指令来实现互斥。代码如下所示：

??? note "Simple Lock With Load/Store"
    ```c
    typedef struct __lock_t {
        int flag;
    } lock_t;

    void init(lock_t* mutex) {
        // 0 --> lock is available
        // 1 --> lock is held
        mutex->flag = 0;
    }

    void lock(lock_t* mutex) {
        while (mutex->flag == 1)
            ;
        mutex->flag = 1;
    }

    void unlock(lock_t* mutex) {
        mutex->flag = 0;
    }
    ```

当第一个线程进入临界区时，会调用 `lock` 来判断锁是否可用，即 `flag` 是否等于 1。然后，线程会将 `flag` 设为 1 以表明当前线程持有锁并进入临界区。在执行完临界区的代码后，线程会调用 `unlock` 将 `flag` 设为 0，不再持有锁

如果第一个线程位于临界区时，此时另一个线程调用 `lock`，由于 `flag` 已经为 1, 该线程将会一直自旋直到持有锁的线程调用 `unlock` 将锁释放。随后，第二个线程将 `flag` 设为 1 并进入临界区

然而，上面的代码存在两个问题
其一是**正确性**(correctness)，这种实现无法保证互斥。如果在第一个线程执行完判断的时候发生了中断，系统将上下文切换到另一个线程。由于第一个线程还未将 `flag` 设置为 1，导致两个线程都将持有锁并进入临界区。整个过程如下图所示

![](Pasted%20image%2020261102191514.png)

其二是**性能**，如果一个线程持有锁，那么等待锁的线程将会不停的**自旋等待**(spin waiting)直到持有锁的线程释放锁，期间将会浪费整个时间片。这种浪费在单处理器上尤为致命，等待者在使用 CPU 时只能空转，导致持有锁的线程根本无法运行，在下一次上下文切换发生之前，系统除了空转无法进行其他工作

### Test-and-Set

由于关闭中断和使用简单的指令都不能正确地构建锁，我们需要更多的硬件支持

硬件提供的最简单的方法是**测试并设置**(test and set)又称为**原子交换**(atomic exchange)，test-and-set 的语义可以使用下面的 C 代码来表示

```c
int test_and_set(int* oldptr, int new) {
	int old = *oldptr;  // fetch old value at oldptr
	*oldptr = new;		// set the new value
	return old;			// return the old value
}
```

test-and-set 指令首先通过地址获取旧值，然后将该地址设置为新值，最后返回旧值，整个过程是**原子性**的。之所以叫做 test-and-set，是因为这个指令在返回旧值以供测试（test）的同时设置（set）新值

下面的代码展示了如何使用 test-and-set 实现一个自旋锁

??? note "Spin Lock With Test-and-Set"
    ```c
    typedef struct __lock_t {
        int flag;
    } lock_t;

    void init(lock_t* lock) {
        // 0 --> lock is available
        // 1 --> lock is held
        lock->flag = 0;
    }

    void lock(lock_t* lock) {
        while (test_and_set(&lock->flag, 1) == 1)
            ;
    }

    void unlock(lock_t* lock) {
        lock->flag = 0;
    }
    ```

假设还没有线程持有锁，当第一个线程进入临界区并调用 `lock` 时，`test_and_set` 指令将返回旧值 0，表明锁未被持有，线程将跳出循环；同时，该指令将 `flag` 设为 1，表明当前线程持有该锁。随后线程将进入临界区，在执行完临界区的代码后，调用 `unlock` 将 `flag` 设为 0 以释放锁

如果在第一个线程位于临界区时，有另一个线程调用 `lock`，由于 `flag` 已经为 1, `test_and_set` 将在返回 1 的同时将 `flag` 设为 1，这会导致第二个线程一直自旋直到持有锁的线程调用 `unlock` 将锁释放。随后，第二个线程将 `flag` 设为 1 并进入临界区

上面的讨论解释**自旋锁** (spin lock)的得名由来。它是最容易构建的锁，在等待锁可用期间，线程单纯地通过循环自旋来消耗 CPU 周期

!!! tip "自旋锁的限制"
    要想让自旋锁在**单处理器**上正常工作，系统必须采用**抢占式调度器**，以便切换到其他线程运行。如果没有抢占机制，一个在 CPU 上自旋的线程永远不会主动放弃 CPU，这会导致持有锁的线程没有机会运行，自然也就永远无法释放锁

接下来我们使用之前的三个标准评估一下自旋锁的表现：

- **正确性**：自旋锁能够正确实现互斥，确保同一时刻最多只有一个线程能够进入临界区
- **公平性**：自旋锁不提供任何公平性，竞争锁的线程可能会一直自旋，从而导致饥饿问题
- **性能**：在单处理器上，自旋锁的性能非常糟糕，如果在一个线程持有锁后发生上下文切换，其他线程只能自旋直到持有锁的线程释放锁；而在多处理器上，只要临界区比较短，自旋锁的性能就相当不错

### Compare and Swap

硬件提供的另一种机制是**比较并交换**(compare and swap, or compare and exchange)，其语义可以使用下面的 C 代码来表示

```c
int compare_and_swap(int* ptr, int expected, int new) {
	int origin = *ptr;
	if (origin == expected)
		*ptr = new;
	return origin;
}
```

`compare_and_swap` 指令会测试 `ptr` 指向的值是否等于 `expected`，如果相等则将其指向的值设为 `new`；否则什么也不做。无论哪种情况该指令最终都将返回旧值，并且整个过程是**原子的**

在使用 compare-and-swap 构建自旋锁时，只需要将 `lock` 的内容替换为以下代码即可

```c
void lock(lock_t* lock) {
	while (compare_and_swap(&lock->flag, 0, 1) == 1)
		;
}
```

compare-and-swap 是一个功能相当强大的指令，在构建**无锁同步**(lock-free synchronization)时非常有用。但在构建自旋锁时，它与 test-and-set 的行为没有什么区别

### Load-Linked and Store-Conditional

一些平台提供了一对指令用于协同构建临界区，例如，MIPS 架构中的**链接加载**(load-linked, LL) 和 **条件存储**(store-conditional, SC) 指令被用来构建锁与其他并发数据结构。它们的语义可以使用下面的伪代码来表示

```c
int LoadLinked(int* ptr) {
	return *ptr;
}

int StoreConditional(int* ptr, int value) {
	if (no update to *ptr since LL to this address) {
		*ptr = value;
		return 1;
	} else {
		return 0;
	}
}
```

LL 和普通的加载指令类似，将内存地址中的数据加载到寄存器。主要区别是在 SC 指令上，只有从执行 LL 开始到执行 SC 结束的时间段内，没有其他指令修改 `ptr` 处的值，SC 才会将 `ptr` 处的值改为 `value` 并返回 1 表示修改成功；否则，SC 不会修改 `ptr` 处的值，而是直接会返回 0 表示失败

下面的代码展示了如何使用 LL/SC 构建一个锁，实现中只有 `lock` 的部分与之前的不同，因此这里只给出 `lock` 的代码

```c
void lock(lock_t* lock) {
    while (1) {
        while (LoadLinked(&lock->flag) == 1)
            ;
        if (StoreConditional(&lock->flag, 1) == 1)
            return;
    }
}
```

利用 C 语言逻辑或运算符的短路求值特性，上述代码还可以简化为更紧凑的形式：

```c
void lock(lock_t* lock) {
	while (LoadLinked(&lock->flag) || 
		!StoreConditional(&lock->flag, 1)) 
		;
}
```

一个线程将会自旋直到 `flag` 被设为 0，然后它将使用 SC 尝试获取锁。如果成功，线程将原子地把 `flag` 设为 1 并进入临界区

假设有两个线程几乎同时调用 `lock`，并且都通过 LL 指令得到了 `flag` 为 0，随后它们会同时尝试执行 SC 指令。此时硬件会保证只有一个线程的 SC 能够率先成功并将 `flag` 修改为 1；而另一个稍慢的线程在执行 SC 时，由于检测到 `flag` 的值在此期间已被修改，其 SC 指令就会失败并返回 0

### Fetch and Add

硬件提供的最后一个机制是**获取并增加**(fetch and add)，它原子性的将特定地址的值加一并返回旧值，其语义用 C 语言表示如下

```c
int FetchAndAdd(int* ptr) {
	int old = *ptr;
	*ptr = old + 1;
	return old;
}
```

可以使用 fetch-and-add 构建一个具有公平性的 ticket 锁，其代码如下：

??? note "Ticket Lock With Fetch-and-Add"
    ```c
    typedef struct __lock_t {
        int ticket;
        int turn;
    } lock_t;

    void lock_init(lock_t* lock) {
        lock->ticket = 0;
        lock->turn = 0;
    }

    void lock(lock_t* lock) {
        int myturn = FetchAndAdd(&lock->ticket);
        while (lock->turn != myturn)
            ;
    }

    void unlock(lock_t* lock) {
        lock->turn = lock->turn + 1;
    }
    ```

我们使用 `ticket` 和 `turn` 两个变量一起构建这个锁，全局变量 `lock->turn` 用来决定哪一个线程将要运行。当一个线程希望持有锁时，它会调用原子指令 fetch-and-add 并根据 `ticket` 获得一个 turn (`myturn`)，当 `myturn == lock->turn` 时，当前线程将获得锁并进入临界区。而 `unlock` 只是将全局的 `turn` 加一

Ticket 锁保证了公平性，只要线程获得了 ticket 值，它最终肯定会被调度

### Avoid Spinning

基于硬件的自旋锁简单却有效，然而在有些情况下，其将会变得非常低效。比如之前讨论过的在单处理器上运行两个线程的场景，一旦持有锁的线程在临界区内被抢占，另一个等待锁的线程就会浪费整个时间片，这个问题在 $N$ 个线程争用一个锁时更为严重，$N-1$ 个时间片将会被浪费

一个简单的方法是在需要自旋时直接放弃 CPU 让另一个线程运行，操作系统通常会提供一个 `yield()` 系统调用让线程能够放弃 CPU。`yield()` 会将当前线程由 [**运行**(running)状态](./1.md#process-status)转为**就绪**(ready)状态，将另一个线程由就绪转为运行


对于只有两个线程的情况，这个方法表现的相当好：未持有锁的线程让出 CPU 后持有锁的线程会继续运行，避免了 CPU 空转

对于多个线程频繁争用一个锁的情况，可能会出现多个线程反复 `yield` 直到持有锁的线程运行的情况。此时，虽然避免了自旋耗尽时间片，但是频繁的进行上下文切换的将导致其成本不可忽视。除此之外，这种方法不能解决饥饿问题，某些线程可能会在无休止的让出过程中永远抢不到锁

前面这些方法的主要问题是完全由调度器决定下一个运行的线程，如果调度器做出了错误的决定，系统可能会造成 CPU 浪费并且导致饥饿。因此我们需要保留一些控制权来决定下一个运行的线程：使用一个队列来记录等待获取锁的线程

为了简化讨论，这里使用两个 Solaris 提供的系统调用：

- `park()`：将调用的线程设为休眠
- `unpark(threadID)`：唤醒 `threadID` 指明的线程

代码如下所示：

??? note "Spin Lock With Test-and-Set and Queue"
    ```c
    typedef struct __lock_t {
        int flag;
        int guard;
        queue_t* q;
    } lock_t;

    void lock_init(lock_t* m) {
        m->flag = 0;
        m->guard = 0;
        queue_init(m->q);
    }

    void lock(lock_t* m) {
        while (TestAndSet(&m->guard, 1) == 1) 
            ;
        if (m->flag == 0) {
            m->flag = 1;
            m->guard = 0;
        } else {
            queue_add(m->q, gettid());
            m->guard = 0;
            park();
        }
    }

    void unlock(lock_t* m) {
        while (TestAndSet(&m->guard, 1) == 1)
            ;
        if (queue_empty(m->q))
            m->flag = 0;
        else
            unpark(queue_remove(m->q));

        m->guard = 0;
    }
    ```

关于上面的代码，有以下几点需要注意：

- **结合 test-and-set 与队列**：`guard` 只负责保护 `flag` 和队列的操作，自旋仅发生在这几行代码内。用户临界区内的等待者则通过 `park()` 休眠，不再空耗 CPU。
- **队列保证公平**：等待线程按入队顺序依次获得锁，因此不会饥饿。
- **锁的直接移交**：`unlock` 唤醒线程时不会清零 `flag`，锁直接传递给被唤醒的线程，该线程无需再次竞争。
- **潜在的竞态条件**：如果线程在释放 `guard` 之后、调用 `park()` 之前被切换走，而恰好此时持有锁的线程调用了 `unpark`，那么该线程之后会永远休眠。Solaris 通过 `setpark()` 解决这个问题。


### Two-Phase Locks

**两阶段锁** (two-phase lock) 将自旋与休眠进行**结合**，它意识到如果锁很快就会被释放，那么短暂的自旋反而比直接休眠更高效。因此，它获取锁的过程分为两个阶段：

1. **第一阶段**：线程会先自旋一段时间，寄希望于持有锁的线程能在这期间释放锁，从而直接拿到锁。
2. **第二阶段**：如果在第一阶段的自旋期内未能获得锁，调用线程就会进入休眠状态，直到锁重新可用时再被唤醒。

> Linux 的 `futex` 就是一种典型的两阶段锁，不过它在第一阶段只自旋一次，一旦失败便直接进入内核休眠。

## Conditional Variable

### Definition

**条件变量**(Condition Variable)是操作系统提供的一种用于线程间状态同步的显式等待队列，其会将不满足某些条件的线程放入队列，在条件改变后唤醒其中一个（或多个）线程

按照之前对 Pthread API 的介绍，可以使用 `pthread_cond_t c` 声明一个条件变量 `c`，其支持 `wait` 和 `signal` 两种操作：

- `wait`：当条件不满足时，将调用线程转为休眠状态并加入等待队列
- `signal`：当条件发生改变后，唤醒正在队列中等待的线程

其定义如下：

```c
int pthread_cond_wait(pthread_cond_t *cond, 
					  pthread_mutex_t *mutex); 
int pthread_cond_signal(pthread_cond_t *cond);
```

> `wait` 需要一个锁作为参数，是为了将**释放锁**与**挂起线程**两个操作合并为一个**原子操作**，从而从根本上消除多线程环境下的丢失唤醒

接下来我们通过一段代码来解释上面的内容：

??? note "Conditional Variable Example"
    ```c
    int done = 0;
    pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
    pthread_cond_t c = PTHREAD_COND_INITIALIZER;

    void thr_exit()
    {
        Pthread_mutex_lock(&m);
        done = 1;
        Pthread_cond_signal(&c);
        Pthread_mutex_unlock(&m);
    }

    void* child(void* args)
    {
        printf("child\n");
        thr_exit();
        return NULL;
    }

    void thr_join()
    {
        Pthread_mutex_lock(&m);
        while (done == 0)
            Pthread_cond_wait(&c, &m);
        Pthread_mutex_unlock(&m);
    }

    int main(int argc, char* argv[])
    {
        printf("parent: begin\n");
        pthread_t p;
        Pthread_create(&p, NULL, child, NULL);
        thr_join();
        printf("parent: end\n");
        return 0;
    }
    ```

假设我们的程序运行在一个单处理器上，这里有两种情况需要考虑

1. 子线程被创建后**父线程继续运行**
	- 父线程会调用 `thr_join()`，获取锁之后检查 `done` 的值以确认子线程是否完成，这里显然还没有。父线程会调用 `wait` 将状态设为休眠并释放锁以等待子线程完成
	- 子线程开始运行后会调用 `thr_exit()`，获取锁后将 `done` 设为 1，然后通过 `signal` 唤醒父线程后释放锁
	- 最后，父线程被唤醒后跳出循环，释放锁后打印信息
2. 子线程被创建后**子线程立即运行**
	- 子线程开始运行后会调用 `thr_exit()`，获取锁后将 `done` 设为 1，调用 `signal` 时队列中并没有线程，因此直接返回
	- 父线程会调用 `thr_join()`，获取锁之后检查 `done` 的值，这里子线程已经完成。父线程不需要进行等待，直接跳出循环，释放锁后返回

> 注意：这里使用 `while` 来判断子线程是否完成而不是 `if`。这可以确保线程从 `wait` 被唤醒后，一定会再次检查共享状态是否真的符合预期，从而有效防范虚假唤醒等问题

在上述实现中，状态变量 `done` 与互斥锁 `m` 都是必不可少的，省略其中任何一个都会导致严重的并发错误：

- 如果不使用状态变量 `done`，在子线程立即运行后，调用 `signal` 唤醒等待队列中的线程，然而此时队列为空，子线程直接返回。当父线程运行时会直接调用 `wait` 后被卡住，因为没有线程会唤醒它
- 如果不使用锁，会导致一个微妙的竞态条件，如果在父线程检查 `done` 并即将陷入休眠时发生了上下文切换，子线程会改变 `done` 的值并唤醒等待队列中的线程，然而此时队列为空，子线程直接返回。当父线程再次恢复运行后，它会继续执行刚才未完成的 `wait` 休眠操作，最终会陷入永久休眠


### Producer/Consumer Problem

**生产者/消费者问题**(producer/consumer problem)，也称为**有界缓冲区问题**(bounded buffer problem)存在着一个或多个生产者和消费者。生产者会产生数据并将其放在缓冲区内；消费者会从缓冲区获取数据并以某种方式使用数据

因为缓冲区是一个共享资源，因此需要通过同步机制进行访问以避免出现竞态条件

> 这个问题在现实中十分常见，例如多线程服务器或者 Unix 系统中的**管道**(pipe)命令

为了简化讨论，我们使用一个整数作为缓冲区并且定义两个辅助函数 `put` 和 `get`

```c
int buffer;
int count = 0;

void put(int value) {
    assert(count == 0);
    count = 1;
    buffer = value;
}

int get() {
    assert(count == 1);
    count = 0;
    return buffer;
}
```

- `put` 通过 `assert` 检查缓冲区是否为空，然后将值放入缓冲区并将 `count` 设为 1 表示缓冲区已满
- `get` 通过 `assert` 检查缓冲区是否已满，然后将值从缓冲区取出并将 `count` 设为 0 表示缓冲区已空

这里的同步条件非常明显：只有当 `count` 为 0 时才能放入数据；只有当 `count` 为 1 时才能取出数据，否则将会触发断言错误

需要使用 `producer` 和 `consumer` 两种线程来完成这一任务。因为 `get` 和 `put` 访问了全局缓冲区，所以其存在临界区，但是在周围放置锁是不够的，还需要使用条件变量。下面是一次存在问题的尝试：

??? note "Producer/Consumer Problem"
    ```c
    int loops; // must initialize somewhere...
    cond_t cond;
    mutex_t mutex;

    void* producer(void* arg) {
        int i;
        for (int i = 0;i < loops;++i) {
            Pthread_mutex_lock(&mutex);				// p1
            if (count == 1)							// p2
                Pthread_cond_wait(&cond, &mutex);	// p3
            put(i);									// p4
            Pthread_cond_signal(&cond);				// p5
            Pthread_mutex_unlock(&mutex);			// p6
        }
    }

    void* consumer(void * arg) {
        int i;
        for (int i = 0;i < loops;++i) {
            Pthread_mutex_lock(&mutex);				// c1
            if (count == 0)							// c2
                Pthread_cond_wait(&cond, &mutex);	// c3
            int tmp = get();						// c4
            Pthread_cond_signal(&cond);				// c5
            Pthread_mutex_unlock(&mutex);			// c6
            printf("%d\n", tmp);
        }
    }
    ```

对于只有一个生产者和消费者的情况，上面的程序没有任何问题。但是如果系统中存在多个生产者或消费者线程，这个程序将会出现严重的问题

#### First Issue

第一个问题出在使用 `if` 检查条件

假设系统中存在两个消费者 $T_{c1}$ 和 $T_{c2}$ 以及一个生产者 $T_p$

1. 消费者 $T_{c1}$ 首先运行，因缓冲区为空而进入休眠
2. 生产者 $T_p$ 放入数据并唤醒 $T_{c1}$，将其移入**就绪队列**，随后 $T_p$ 在下一轮循环中因缓冲区已满也进入休眠
3. 另一个消费者 $T_{c2}$ 抢在 $T_{c1}$ 之前运行并取走了唯一的数据。等到 $T_{c1}$ 随后运行时，由于使用的是 `if`，它从 `wait` 返回后不会重新检查条件，而是直接向下调用 `get()`，最终因缓冲区早已被掏空而触发断言错误

出现这个问题的主要原因是在由生产者 $T_p$ 唤醒的线程 $T_{c1}$ 运行前，缓冲区的状态已经发生了变化

现代系统通常使用 **Mesa 语义**，唤醒线程只是作为一个提示但不能保证被唤醒的线程立刻开始运行

解决这个问题只需要将 `if` 改为 `while` 即可，在 Mesa 语义下，永远使用 `while` 检查条件

#### Another Issue

另一个问题是只使用了一个条件变量

1. 两个消费者 $T_{c1}$、$T_{c2}$ 首先运行，皆因缓冲区为空而进入休眠。
2. 生产者 $T_p$ 放入数据并唤醒 $T_{c1}$，随后在下一轮循环中因缓冲区已满也进入休眠。
3. $T_{c1}$ 取走数据后发出唤醒信号并再次休眠。如果它唤醒的是另一个消费者 $T_{c2}$ 而非生产者 $T_p$，$T_{c2}$ 醒来发现缓冲区仍为空便会继续休眠，最终导致所有线程陷入永久沉睡

这个问题的解决办法是使用两个条件变量，让生产者和消费者分别在不同的队列上等待，确保同类线程不会互相唤醒

#### Solution

下面是生产者/消费者问题的正确代码，使用了两个条件变量和 `while` 进行条件测试：

??? note "Producer/Consumer Problem Solution"
    ```c
    cond_t empty, fill; 
    mutex_t mutex; 
    void *producer(void *arg) { 
        int i; 
        for (i = 0; i < loops; i++) { 
            Pthread_mutex_lock(&mutex); 
            while (count == 1) 
                Pthread_cond_wait(&empty, &mutex); 
            put(i); 
            Pthread_cond_signal(&fill); 
            Pthread_mutex_unlock(&mutex); 
        } 
    } 

    void *consumer(void *arg) { 
        int i; 
        for (i = 0; i < loops; i++) { 
            Pthread_mutex_lock(&mutex); 
            while (count == 0) 
                Pthread_cond_wait(&fill, &mutex); 
            int tmp = get(); 
            Pthread_cond_signal(&empty); 
            Pthread_mutex_unlock(&mutex); 
            printf("%d\n", tmp); 
        } 
    }
    ```

### Covering Conditions

在某些场景下，不同的等待线程需要满足各自不同的条件才能继续执行。此时如果仅调用 `signal` 随机唤醒一个线程，由于无法预知队列中具体哪个线程的条件已得到满足，很可能会唤醒错误的线程并导致程序卡死

解决的办法是用 `pthread_cond_broadcast` 替换 `pthread_cond_signal`，一次性唤醒**所有**等待线程，让它们醒来后各自重新检查条件。这种通过广播来唤醒所有线程的策略被称为**覆盖条件** (covering condition)，因为它能够保守地覆盖所有潜在的唤醒需求

> 覆盖条件会带来额外的性能开销，因为许多尚未满足条件的线程被唤醒后又得立刻重新休眠。因此，只有在无法确定具体该唤醒哪个线程的场景下才应使用 `broadcast`，而在普通的生产者/消费者模型中使用 `signal` 即可
